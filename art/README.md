# Cinderbelt – Art Handbook

Everything visual in the game (ship parts, asteroids, stations, VFX, UI art,
planets) is **generated by Python scripts run in Blender headless**. Nothing is
downloaded or hand-modelled. This file explains how to continue that work
without any prior context.

* Blender: your Blender executable (e.g. `blender` on PATH), 5.2 LTS; Cycles with a GPU (OptiX) for renders.
* Every command: `"<blender>" --background --factory-startup --python art/blender/<script>.py -- <args>`
* Only `art/` and `public/assets/` belong to the artist. The game code lives in `src/` (other agents).
  The art agent does **not** run git.
* The skybox (`art/blender/skybox.py`, `skybox_lib/`) is owned by a separate artist – don't edit it. After `skybox.py --publish` run `npm run assets:optimize -- --only skybox` (the game loads `ring<N>_bg.webp`, §2.9).
* **Every build ends with the optimizer post-step** (`art/tools/optimize_assets.mjs`, §2.9): `build_all.py`, `planets.py`, `gas_giant.py` and `vfx.py --only explosions` call it themselves; anything else → `npm run assets:optimize` (needs Node + `npm install`). `npm run assets:check` lists what is not optimized, and a game test fails on an unoptimized GLB.

### `build_all.py` flags

```
--only parts,pirate_parts,asteroids,stations,station_variants,hangar_bay,debris,props,clutter,wreckage,pois,
       guild,borders,npc,landmarks,scenery,liveries,icons,decals,vfx_borders,preview,menu2
                                 (default: all stages, in that order)
--names a,b                      with pois/stations: build only these files (e.g. --names ozvena_beacon,station_home)
--tiers iron[,titanium,crystal]  part tiers (default iron,titanium,crystal)

--no-optimize                    skip the optimizer post-step (debugging the raw Blender export only)
```

Stages:
* **parts** – `parts/<module>.py` for each name in `PART_MODULES`, every tier → `public/assets/models/parts/<module>_<tier>.glb`, plus `hull_connector_edge.glb` / `hull_connector_corner.glb`.
* **pirate_parts** – `build_pirate_parts.build()` + `write_manifest()` → `public/assets/models/parts_pirate/` (§2.7.21). Check the result with `build_pirate_parts.py -- --verify-only`.
* **asteroids** – `asteroids.py` `VARIANTS` (12 rocks; iron/copper/titanium get ore veins, see §2.7.1) + `FRAGMENTS` (12) → `public/assets/models/asteroids/` + `veins.json`.
* **stations** – `structures.py` `BUILDERS` + `hangar.py` → `public/assets/models/stations/` (incl. the batch D dock clamp v2, caged beacons and hangar platform v2, §2.7.25); writes `art/blender/data/station_layouts.json` (`structures.LAYOUTS` + the batch D variants' `stations_var.LAYOUTS_D`) and prints a `COVERAGE` line per station (fraction of vertices outside every collision circle, max distance outside).
* **station_variants** – `batch_d.build({'variants'})`: `stations/station_d`, `station_e`, `outpost_c`, `outpost_d` + `art/blender/data/station_layouts_batch_d.json` (§2.7.25).
* **hangar_bay** – `batch_d.build({'hangar'}, {'hangar_bay'})`: `stations/hangar_bay.glb` (`HEIGHT RULE` line). After the optimizer, when either batch D stage ran, `batch_d.write_manifest` updates `stations/stations_batch_d.json` (it records the shipped byte sizes).
* **debris** – `debris.py` `BUILDERS` → `public/assets/models/debris/debris_a..e.glb`, `debris_pirate_a..e.glb`, `debris_kovaci_a..c.glb` (batch B1/B2, §2.7.23).
* **props** – `props.py` `BUILDERS` → `public/assets/models/props/` (`cargo_container.glb`, exported **without** vertex colours – keep it that way, the file is byte-identical).
* **clutter** – `batch_b.build_props()`: `props.CLUTTER` (13 space-clutter props, B4/B5) **with** vertex colours + `props/props.json` (§2.7.23).
* **wreckage** – `batch_b.build_wreckage()`: `models/wreckage/*.glb` + `wreckage.json` (§2.7.23).
* **pois** – `build_all.poi_jobs()` (**M5b:** `base_modules.py` → `models/base/`, `drones.py` → `models/drones/`): `pirates.py` (→ `models/pirates/`, writes `art/blender/data/fortress_layouts.json` and a `COVERAGE` line), `kovaci.py` (→ `models/kovaci/`), `anomalies.py` (→ `models/anomalies/`), `giants.py` (→ `models/asteroids/asteroid_giant_*.glb`), `buoys.py` (→ `models/props/buoy_*.glb`); **M4:** `derelicts.py` (→ `models/derelicts/`), `comet.py` (→ `models/comets/`), `trader.py` (→ `models/npc/`), `home_modules.py` (→ `models/stations/home_module_*.glb`); **M5a:** `wardens.py` + `kolos.py` (→ `models/kovaci/`). `build_all.LAYOUT_FILES` writes `derelict_layouts.json`, `boss_layouts.json`, `home_modules.json`, `base_modules.json`, `drones.json` to `art/blender/data/` **after** the builds (Kolos needs its planned veins). Every module with `LAYOUTS` gets a `COVERAGE` line (drifting pieces / comet tail excluded).
* **guild**, **borders**, **npc** – `batch_c.build_guild/build_borders/build_npc` (§2.7.24): `npc/guild_cutter`, `guild_frigate`, `stations/guild_picket`; `models/borders/*.glb`; `npc/miner_barge`, `tanker`, `courier`, `survey_ship`. Each run updates the build report `art/out/batch_c_report.json` and regenerates `npc/npc_ships.json` + `borders/borders.json` from it.
* **landmarks** – `landmarks.build()` → `public/assets/models/landmarks/*.glb` + `landmarks.json`, `vfx/echo_column.png` (§2.7.20).
* **scenery** – `scenery.build()`: `models/scenery/*.glb` + `scenery.json` (§2.7.22).
* The batch A–C stages override the batches' private atlas dirs (`art/out/palette_batch_*`, used while the batches ran in parallel) with the shared `art/out/palette/` (same pixels) and leave optimizing to the post-step below. Their own entry scripts (`scenery.py`, `batch_b.py`, `batch_c.py`, `batch_d.py`) still work for quick iteration.
* **liveries** – `lib/livery.py` → `public/assets/textures/palette_<livery>_{basecolor,orm,emissive}.png` for `default`, `pirate`, the M4 paints `paint_graphite|sand|navy|racing` and `derelict` (§3, §2.7.21). Also writes **`public/assets/textures/palette_swatches.json`** (`palette.write_swatch_table`, §3.1): swatch key → atlas UV for geometry the game builds at runtime (hull shell).
* **optimize** (post-step after the liveries stage, whenever a model stage ran) – `lib/optimize.run(['models'])` → `art/tools/optimize_assets.mjs` (§2.9). It runs after **liveries** because it compares every embedded atlas with the shipped `palette_default_*`.
* **icons** – `icons.py` → `public/assets/icons/parts/<partId>_t<1|2|3>.png`, `icons/resources/<id>.png`.
* **decals** – `batch_b.build_decals()` → `vfx/damage_decals.png` (numpy, §2.7.23). **vfx_borders** – `vfx_borders.main()` → `vfx/border_ribbon.png`, `border_fence_<security>.png` (numpy, §2.7.24).
* **preview** – `preview.py main(mode)`: `m1` (M1 sheet/ship/connectors), `m2` (tiers/titanium ship/asteroids), `m2s` (`preview_stations.py`), `m3` (`preview_m3.py`: combat parts, debris, pirate livery, icons).
* **menu2** – last, because it renders the shipped (optimized) GLBs: `ui_art.render_menu2((build_all.MENU2_OPTION,))` (option 1, ~15 s on the GPU) + `finalize_menu2` → `ui/menu_bg.jpg`, `menu_bg_1080.jpg` (§2.7.25 D4). The JPGs are written with the fresh-scene view settings (AgX, no look) like the standalone `--final2` run. Cycles + the denoiser are not bit-exact: a rebuild differs by ~0.07/255 on average (max ~20/255 on a few pixels) – keep the committed JPGs unless the scene changed.

Typical commands:
```
build_all.py -- --only parts --tiers iron              # iterate on one part tier quickly
build_all.py -- --only parts,icons,preview --iter v22  # rebuild parts + icons + M3 previews
build_all.py -- --only stations,preview --preview m2s  # stations + their previews
build_all.py                                           # everything (do this after any palette change)
```

## 2. Modelling and export conventions (the game depends on these)

### 2.1 Units and axes
* 1 Blender unit = 1 ship-grid cell = 1 game unit.
* Blender **+X = bow / forward / dock direction, +Y = port (left), +Z = up**, z = 0 = gameplay plane.
* glTF export is Y-up: Blender (x, y, z) → glTF (x, z, −y). So in glTF +X forward, +Y up, +Z starboard.
* Ship parts: rotation 0 faces +X. An engine at rotation 0 pushes toward +X (nozzle at −X).

### 2.2 Ship parts (1×1)
* Footprint x, y ∈ [−0.485, 0.485] (`common.HALF`) → a 0.03 seam between neighbours; parts must never exceed ±0.5.
* Deck profile (all parts): dark core block z −0.20…0.10, side skirt stripe (tier accent) z −0.115…−0.055 protruding 0.006, light deck plate z 0.06…**0.20** (`DECK_TOP`), plate half 0.478, chamfer 0.03, plate bevel 0.012, core bevel 0.01. Tier ≥ 2 adds a glow line on the core sides (z 0…0.018) and corner L-brackets.
* Lowest geometry: engine bell, z ≈ −0.356.
* Engines: core block only from x = −0.12 (plate from −0.115); the nozzle occupies the rear half.
* Parts are built from `C.core_block(tier=t)` + `C.deck_plate(mat=t['plate'])` + details; keep everything above the deck clear of neighbours.
* Triangle budget ≈ 3k per cell (1×1 max: tractor_beam_titanium 3360, shield_generator_titanium 3140; 2×1 heavy_laser_titanium 6564, cruise_drive 4.0–4.4k; 2×2 large_cargo_titanium 4276, large_reactor_titanium 7.3k).
* File names: `<module>_<tier>.glb` (tier = iron | titanium | crystal). ### 2.2.2 T3 "crystal" tier (M5a)
* `palette.TIERS['crystal']`: level 3, plate `hull_cr` (pearl white with a lilac cast, glossier), core `hull_dark_cr` (deep indigo), accent `accent_crystal` (renders ≈ UI `--af-crystal` #b98cff), glow `tier_glow_cr` (violet), `gem` = `cr_gem` (cut-crystal gradient swatch: saturated violet root → lighter violet tip, low emission).
* Same footprint, deck heights, nodes/pivots and connector compatibility as T1/T2 – every `lvl >= 2` detail is inherited (in violet) plus T3-only cues: `common.core_block` adds a **violet crystal inlay ring** around the top of the deck plate (`frame_ring`, z DECK_TOP−0.004…+0.007, inset 0.024 – under a connector strap it is simply covered); `common.corner_brackets` returns **cut-gem bars across the plate corners** (`crystal_corners`, mirrors the UI T3 "fazety" brackets) instead of the L-brackets; each part adds hero crystals (`common.gem` = cut prism along +Z, `common.gem_bar` = elongated cut gem, `common.place` = orient + move): cockpit crystal spine + fin tips, engine crown of focusing crystals on the upper bell rim, laser/heavy laser focusing prisms + gem ridge, reactor/large reactor/refinery crystal caps, gyro double-pointed crystal core, cargo seal bar + gem posts, fuel-tank gem gauges, radar crystal feed, cannon accelerator rails, shield crystal emitter tips, armor crystal bar + one bold chevron, battery gem bus, shielding crystal lattice, repair crystal welding focus.
* Lesson: pastel violet + emission washes to white under AgX/ACES. Keep the T3 swatches **saturated with low emission** (cr_gem 1.0, glow 2.2) – the first pass (pale lilac, emission 2–3) read as "white T2".

### 2.2.1 Multi-cell parts (2×1, 2×2, …)
* A part module declares `CELLS = (w, h)`: w cells along X (forward), h along Y. No attribute = (1, 1).
* **The model is centred on the centre of its footprint at rotation 0.** A 2×1 spans x ∈ [−1, 1], y ∈ [−0.5, 0.5] (long axis along +X = forward); a 2×2 spans x, y ∈ [−1, 1]. The game puts the part origin at the centre of its occupied cells (a 2×1 on cells (3,0),(4,0) → origin (3.5, 0)); rotating by 90°/270° swaps w and h.
* Same deck height, base profile and side trim as 1×1 parts. The ±0.485-style margin (0.015) exists **only on the outer perimeter**: `common.footprint(w, h)` → core half extents (w/2 − 0.015, h/2 − 0.015), `common.plate_half(w, h)` → plate half extents (w/2 − 0.022, h/2 − 0.022). `common.hull_base(tier, w, h)` builds ONE continuous core block + skirt (+ tier glow) + deck plate – **no internal seams** – so the part sits flush next to 1×1 parts and hull connectors work on its outer edges.
* `common.corner_brackets(..., hx=, hy=)` takes the plate half extents for multi-cell plates.
* Turrets on multi-cell parts stay inside the whole footprint at every allowed aim angle (heavy laser: pivot above the front-cell centre, lens tip 0.53 from the pivot; checked in the `m2d-parts.png` footprint tile).
* Icons frame the whole footprint (`icons.part_icons`: ortho scale × 0.9·max(w, h)), bow up, same 128 px plate.

### 2.4 Hull connectors
* `hull_connector_edge.glb`: origin = centre of the seam between two orthogonally adjacent cells; modelled for a seam at x = 0 running along Y. Neighbours (x,y),(x+1,y) → place at (x+0.5, y), rot 0; neighbours (x,y),(x,y+1) → at (x, y+0.5), rot 90°.
* `hull_connector_corner.glb`: where all four cells (x,y),(x+1,y),(x,y+1),(x+1,y+1) are occupied → at (x+0.5, y+0.5).
* Tier-neutral (dark skirt bridge, metal hub). Strap length ±0.13 so it never overhangs an engine's open rear half.
* Reference implementation: `preview.connector_placements()`.
* **Multi-cell parts:** work on the occupied cells with an owner (part index) per cell. Edge connector only between orthogonal neighbours owned by **different** parts (never on a part's internal seam); corner connector where all four cells are occupied **unless all four belong to the same part** (a T-junction where a 2×1 meets two other parts gets a cap; the centre of a 2×2 does not). Reference: `preview_m2d.connector_placements_multi(layout)` / `part_cells(layout)`.

### 2.5 Stations, dock_port, hangar
* Station radius R: home 14, stations A/B/C 10, outposts 6. `dock_port` empty at (R, 0, 0) = tip of the docking arm on the gameplay plane; `dock_clamp.glb` is placed there (origin = dock_port, cradle opens toward +X, spans x −2.4…0.6, y ±1.5). The docked ship's centre is at `dock_port + (boundingRadius + 1)` along +X, bow pointing back at the station.
* Stations are not in the AF_Palette part budget sense: after the detail pass (§2.10) home ≈ 64k tris, stations A/B/C 16–25k, outposts 4.5–5.2k, clamp 1.4k. They carry COLOR_0 (AO + grime) and are exported with vertex colours.
* `hangar_platform.glb`: 17×17, centred on the origin, 15×15 build grid with cell centres on integer coordinates −7…7, seams on half-integers. **Floor top z = −0.37** (just below the engine bell, so no part clips). Gantry/rails/crane stay outside the 15×15 area.

### 2.7.1 Asteroid ore veins (`veins.py`)
* Iron, copper and titanium rocks (`asteroid_<res>_<a|b|c>.glb`, unchanged file names; **ice has no veins**) carry 1–3 veins (the planner aims for 2 on a/b and 3 on c and drops what does not fit). Each vein is a gently meandering seam **across part of the surface**: arc length 2.2–3.6 units, never wrapping around (chord ≥ 0.62·length), no near-parallel neighbours, kept away from the crystal clusters, mid-point on the camera-facing upper side.
* Look: a **chiselled groove** carved into the rock (EXACT boolean with a swept trapezoid: flat floor, walls sloping `WALL_SLOPE` 0.95, depth ≈ 0.13·scale, ramps out of the surface at both ends) holding a faceted **ore fill** (ridge at `RIDGE` 0.45 of the depth with per-row jitter → crystalline facets; slight emission from the `st_band_<res>` swatch) plus a few sparse resource crystals (`st_ore_<res>`) sunk into the seam. Groove faces are tinted per face in the rock's vertex colour (dark crevice rim, never black). Rock shape, clusters and nuggets use the same seeds as before; veins use their own RNG (`seed*7919+13`); only nuggets that would sit in a groove are dropped.
* Export: each fill is a **separate child mesh node `Vein_<i>`** (identity transform under the rock root, so its local coordinates = the rock's) with `TEXCOORD_0` (atlas), **`TEXCOORD_1`** (u = normalised arc length 0..1 along the vein, v = 0..1 across the fill: 0 left edge, 0.5 ridge, 1 right edge; the packed crystals use v = 0.5 and the u of their position) and `COLOR_0` (ridge bright, edges/ends darker). The game shader moves a bright "active segment" along u. Preview stand-in: `preview_m2d.vein_material()` (emission × (1 + 3·mask) + resource colour, mask = u ∈ [0.4, 0.6] with 0.04 soft edges).
* Triangles: rock + veins 2.4–3.7k (max copper_c 3684; the grooves add ~300–600 over the old rocks).
* **Per-kind vein parameters** (`veins.KIND_PARAMS`, M5a): `crystal` ("singing") – 1/2/2 veins (round/elongated/chunky), arc 2.6–3.6, sparse **tall tuning crystals** (spacing 0.62–0.95, height 1.9–2.8× groove depth); `rare` ("fast") – always 3 veins, arc **1.25–1.8**, densely packed small emerald crystals (spacing 0.30–0.42). `veins.plan(..., kind=)` applies them; iron/copper/titanium keep the old rules. `veins.VEIN_TYPE` maps kind → mechanic.

### 2.7.2 `veins.json`
`public/assets/models/asteroids/veins.json`, written by the asteroids stage (`veins.json_entry`):
```
{ "_schema": {...},
  "asteroid_iron_a": { "veins": [
      { "node": "Vein_0", "length": 2.4131,
        "points":    [[x, y, z], ...],      21 points, glTF local coords (Y up), ordered along u
        "u":         [0.0, ..., 1.0],       u of each point = TEXCOORD_1.u of that fill row
        "normals":   [[x, y, z], ...],      outward surface normal per point (unit)
        "halfWidth": [0.05, ...] }          fill half width per point (groove opening is wider)
    ] }, ... }
```
* `points` = centreline of the fill at ridge height (the faceted ridge vertices wander up to ±0.25·halfWidth sideways), in the frame of the rock root node; `length` = sum of chord lengths; point k has u = cumulative length / length, so u is linear in arc length between points. Active segment: walk the polyline by arc length s, u = s / length.
* Only files with veins are listed (no ice). No copy in `src/` yet – load it from `public/assets` or ask the code agent to copy it.
* M5a added `"type"` to every vein: `drift` (Fe/Cu), `deep` (Ti), `singing` (Kr), `fast` (VZ). The preview stand-in highlights per kind (`preview_m2d.HL` + `preview_m5a_world`).

### 2.7.5 Forge-smiths visual language (ancient star-smiths) + Ozvena
The first glimpse of the ancient civilization must read as **not human**:
* **Form:** 3-fold / radial symmetry, tapering blade (leaf) shapes leaning into spires, faceted diamond sections. Humans build 4-fold boxes on a grid with chamfered plates.
* **Surface:** monolithic and seamless – no plates, seams, bolts, hazard stripes or windows. **Parts levitate** (segmented rings, hovering crystals, base split into floating shards) – nothing is bolted on.
* **Materials:** glossy obsidian `kov_obsidian`, forged-bronze edge inlays `kov_bronze`, ember-red glyph channels `kov_ember` (the forge fire – these are the "red glowing parts" the pirates collect), violet "singing" crystal `kov_crystal` (gradient, deep violet root → pale tip; keep its emission low, AgX/ACES wash bright violet to white).
* **Glyphs:** rhythms of short dashes (long-short-short) set into outer faces; never text or human symbols.
* Kit in `kovaci.py`: `loft`, `blade`/`blade_frame`, `glyph_strip`, `seg_ring`, `octa`, `crystal_column` – reuse it for the M5/M6 ruins, Wardens and workshops.
* `kovaci/ozvena_beacon.glb`: tripod of three obsidian blades (6.6 tall) around a crystal heart, two floating segmented rings, hovering octahedral crystal; ~5.6 × 5.6 × 8.5, ~2.3k tris.

### 2.10 Detail pass ("dtl") – greeble kit, density rule, budgets
Large structures used to carry about as many features as a 1×1 part, so at the game camera they read as smooth plastic. The detail pass gives them **ship-part detail density per unit area**.

**Files**
* `lib/greebles.py` is the greeble kit:
  * `Kit` is a light mesh builder (box/prism/plate/cylinder/lathe/decal in a surface frame; greeble bottoms are skipped). It also writes the `af_dirt` vertex attribute used for soot.
  * Greeble types (`TYPES`). Top faces: panel, vent, grille, hatch, unit (machinery block + status lamp), pipes (with brackets), cables, lights, skylight, rack (cargo containers), radiator, truss, tank, antenna, dish, scorch decal, and the opt-in `patch` (welded scrap) and `hole` (missing panel). Walls: window strip (warm emissive + mullions + hood), vent, panel, door (+ lamp), pipes, lights, unit, cables, soot streak.
  * `Scatter` places greebles seeded and deterministic. Each footprint is checked with 5 ray casts: it must sit flat on the host, with nothing above it and no bend under it. A spatial hash prevents overlaps, and `Zones` keep areas clear.
  * `panel_grid()` adds panel insets: raised chamfered plates over a dark `panel_line` underlay, so the gaps read as seams like the ones between ship parts.
  * `wall_rows()` adds continuous window/light bands at given heights.
  * `weather()` bakes COLOR_0: ray-cast AO (near + far), per-face panel fade, grime blotches, darker undersides, soot from `af_dirt`, optional rust tint. Emissive faces stay at 1.
  * `STYLES` hold the swatch roles per type: `home`, `trade` (green trim, racks), `refinery` (pipes/tanks, ice glow), `shipyard` (truss/units), `outpost`, `pirate` (pir_* swatches, patches, rust, red lamps), `derelict` (der_* swatches, dead lights, holes, scorch), `base`.
* `station_kit.py` holds the large-structure blocks: `arc_box`, `rbox`, `bar`, `box_truss`, `tank_h`, `solar_array` (frame + cells + spar, tiltable), `rotator`, `light_row`, `ring_lights`. It also has the finishing pipeline:
  * `finish()` joins the static parts into one mesh plus an optional rotor, then runs `dress()` (panels → window rows → scatter) and `weather()`, bakes to the atlas, and adds beacons and `dock_port`.
  * `post_dress()` does the same for an already finished node, in that node's local space. It recognises faces already baked to the atlas by their UV (`greebles._poly_key`), and `materials.bake_to_atlas` keeps those faces' UVs.
* `stations_dtl.py` has every station, outpost and the clamp. `structures.BUILDERS` delegates to it; the M2/M4 builders are kept as `structures.LEGACY_BUILDERS`. It also holds the generic blocks `hub_dtl` (layered hub with overhang flange and an optional bearing groove for a rotating collar), `ring_dtl` (profiled ring with collars, varied roofs, spoke tubes, hub collar) and `arm_dtl` (walkway deck, side tubes, runway lights, rib collars, under-girder, approach gantry carrying beacons 0/1).
* `dtl_pois.py` applies `post_dress` to the fortress, the derelicts and the planetary base hub/modules. `build_all.build_pois()` calls it right after each builder, and those GLBs are now exported with COLOR_0. Child nodes (animated or toggled) go into the ray-test BVH and get clear zones; spinning nodes get a cylinder that covers their sweep.

**Density rule.** A 1×1 ship part shows about 4–6 distinct features. On large structures the target is:
* tops: `TOP_RATE` 1.8 greebles per unit²;
* walls: `SIDE_RATE` 1.6 per unit²;
* panel insets on every flat top face of 1–1.2 unit² or more (cell 0.8–1.15);
* window bands at fixed heights (rows snap so strips line up).

Features are 0.1–0.9 units. The scatter saturates on its own, because footprints that don't fit are rejected.

**FUNCTIONAL SURFACES STAY CLEAR (user rule).** Nothing goes on surfaces that are used:
* landing and drone pads;
* dock cradle floors and the hangar build floor (or Station C's dry-dock floor);
* walkway decks, such as dock-arm decks and base pad bridges;
* glowing guide markings and chevrons;
* any surface where something lands or docks.

Put detail on the rim, sides, undersides and supporting structure instead. How it is enforced:
1. `floor_dark` is never a greeble host.
2. Every builder declares `Zones.functional(x0, x1, y0, y1, z)` / `Zones.pad(x, y, r, z)` over such surfaces (`stations_dtl.arm_zone`, the clamp cradle, base pads, drone dock, launcher).
3. `Scatter` keeps top greebles at least 0.3 away from small emissive guide faces.
4. Modules with a functional top (`drone_dock`, `launcher`) get side detail only. Example: the drone dock has rim vents and lights, and its pad, chevrons and glow ring are untouched (`detail-dronedock-before-after.png`).

**Other clear zones.** Zones also keep clear the rotor sweep (static detail must stay out of the volume the ring, spokes and collar sweep), the dock clamp and docked-ship corridor (x > R − 2.5, |y| < 1.7), the home-module attach points, beacons, turret mounts, the core well, the spawn lane, and the volumes of animated/toggled nodes.

## 3. Palette / atlas system

* **One material, `AF_Palette`, for every model.** `lib/palette.py` defines `SWATCHES` (key, base hex, metal, rough, optional emission colour + strength, optional gradient). The atlas is `COLS=8 × ROWS=16` cells of `CELL=16` px → **128×256 px, 128 slots, 83 used** (M2d appended `battery_glow`, `battery_dim`, `tractor_glow`, `tractor_glass`; the vein fills reuse the formerly unused `st_band_*` swatches). M3.5 appended `pir_*` (pirate structures: gunmetal, worn plate, rust, hazard ochre, red glow/glass), `kov_*` (Forge-smiths: obsidian, bronze, ember, crystal) and `anom_*` (void, accretion, grav, ion, rad, time, time_ghost) → 102 used. M4/M5a appended `der_plate/dark/rust/window` (derelicts), `comet_ice/crust`, `he3_glow`, `comet_jet`, `accent_trader`, `repair_glow`, `hull_cr`, `hull_dark_cr`, `tier_glow_cr`, `cr_gem` (T3), `rad_core` (shielding absorber), `kov_warden`, `st_rock/ore/band_crystal`, `st_rock/ore/band_rare`, `ex_matter` → 125 used. **M5b grew the atlas to `ROWS = 32` (128×512 px, 256 slots)** – UVs are normalised, a full rebuild re-baked every glb; verified pixel-identical (`m5b-atlas-check.png`: old glb / new glb / |diff|×8, max diff 1/255 on parts, rocks, stations, Kolos; no game code hard-codes the atlas size) – and appended `base_concrete`, `base_concrete_dark` (base pad slabs / foundation), `cruise_glow` (pale-gold He3 plasma, the cruise drive's role colour), `cruise_core` → 129 used. The pirate clan part sets (§2.7.21) appended `pir_rust_patch`, `pir_weld`, `kot_*` (6) and `sst_*` (6) → 143; art batch C appended `guild_navy`, `strobe_blue`, `accent_institute` (§2.7.24) → 146; the SL2 hull-shell torn edges (§3.1) appended `ash` (slot 146) and `hot_edge` (slot 147) → **148 used, 108 free**.
* The formerly stubbed `accent_crystal(_dark)` values were changed (unused before) to `#9466F2` / `#6A3FC0` (renders ≈ `--af-crystal`).
* Three textures: base colour (sRGB), ORM (R=1 unused AO, G=roughness, B=metalness, linear), emissive (sRGB; brightness = emit_strength / `EMIT_MAX` (6.0); the material's emissive strength is EMIT_MAX). Sampler: nearest, clamp. Back faces culled (doubleSided false).
* Modelling uses *logical* materials (`materials.mat('hull_light')` → `PAL_hull_light`); `geo.finalize()` → `materials.bake_to_atlas()` collapses each face's UVs to its swatch centre (gradient swatches spread along u via the `af_grad` vertex attribute) and swaps in AF_Palette.
* **Adding a swatch:** append to `SWATCHES` (never reorder or insert – slot index = position). Then rebuild **everything** (`build_all.py` with no `--only`): every glb is re-baked against the new atlas, the liveries stage writes the new `palette_default_*`, and the optimizer post-step (§2.9) strips the (now identical) embedded copies – the game and all GLBs share `textures/palette_default_*.png`. Shortcut for a purely additive append (no existing swatch changed): `build_all.py -- --only liveries` is enough – shipped GLBs reference the shared atlas by URI and their cells do not change, and every later model build regenerates its embedded atlas from the same `SWATCHES`, so the optimizer still finds it identical (used for `ash` / `hot_edge`).
* **Tiers** (`TIERS`): accent / accent_dark / plate / core / glow / level (/ gem). iron = orange accent, level 1; titanium = blue accent, cooler glossier hull (`hull_ti`, `hull_dark_ti`), glow line `tier_glow_ti`, level 2 (extra detail: fins, brackets, doubled glow); crystal = level 3, §2.2.2. Exotic is still a stub.
* **Liveries** (`lib/livery.py`): a dict of swatch overrides with the same layout; `export_livery(dir, name)` writes `palette_<name>_{basecolor,orm,emissive}.png`. The game swaps the three textures on a cloned material (`flipY = false` to match glTF, basecolor/emissive sRGB, ORM linear). Current: `pirate` (dark gunmetal, rust-red trim, red/amber glows) + `default` + the M4 **paints** `paint_graphite`, `paint_sand`, `paint_navy`, `paint_racing` (override only `hull_light/white/mid/dark`, `hull_ti/dark_ti`, `hull_cr/dark_cr`; preview `m4-paints.png`) + **`derelict`** (computed from every swatch: desaturated, darkened, sooty, no emission – §2.7.21).
* **Vertex colours**: a CORNER `BYTE_COLOR` attribute named `Col`, set active; values multiply the base colour, so only darken/tint (keep albedo swatches slightly light, e.g. the `st_rock_*` swatches). Large flat faces need extra vertices for gradients (see `debris.densify`).


### 3.1 Hull shell (SL2 E1) – runtime geometry on the palette atlas

The hull shell (ship-building design, hull shell) is **built by the game at runtime** (`src/render/hull/`), not exported as GLBs: side band, trim lip, corner guards, seam strips, soot on torn edges, terrace slabs, panel grooves and the nav lights. Every piece is a child of its owner part's node on the same `AF_Palette` material, so it is coloured purely by **UVs into the shared atlas** and follows every livery (paints, pirate, derelict) and per-part tint for free. Mock-up / reference geometry: `art/blender/mockups/ship2_geo.py`.

**Swatch table – `public/assets/textures/palette_swatches.json`** (written by the `liveries` stage, `palette.write_swatch_table`; never edit by hand):

```json
{ "_schema": "af-palette-swatches/1", "_note": "…",
  "atlas": { "cols": 8, "rows": 32, "cell": 16, "width": 128, "height": 512 },
  "swatches": { "hull_light": [0.0625, 0.984375], … },
  "emissive": ["glass_cockpit", "engine_glow", …] }
```

* `swatches`: **every** swatch key (atlas order) → `[u, v]` of its **cell centre** in **glTF / three.js UVs** (`v` measured from the **top** of the PNG – the textures are loaded with `flipY = false`), i.e. exactly what the glTF exporter writes for `swatch_uv(key)`: `(u, 1 − v_blender)`. Gradient swatches give the centre (t = 0.5). One table serves every livery (same layout). Read by `parseSwatches` / `ModelLibrary.swatchUv` (`src/render/assets/ModelLibrary.ts`), which only needs `swatches` (entries must be two finite numbers); `atlas` and `emissive` are informational (the keys whose swatch has an emission colour). The code never hard-codes the atlas size – a missing file switches the shell off.
* Verified against the shipped `palette_default_basecolor.png`: sampling every entry (flipY = false) returns the swatch's base colour (148 entries; gradient swatches give their mid colour).
* **Additive check** (done for `ash` / `hot_edge`): diff the old and new `palette_swatches.json` (only new keys, every old `[u, v]` identical) and compare every `palette_*_{basecolor,orm,emissive}.png` cell by cell – only the new slots may change.
* **Adding a swatch:** appending to `SWATCHES` + the liveries stage refreshes the table; reordering would move every UV (forbidden anyway, §3).

**Constants** (one truth with `src/render/hull/shellConstants.ts`; 1 = one grid cell; *out* = along the outward normal of an outline edge from the cell edge, negative = inward; *z* = model height, part deck top `DECK_TOP` = 0.20):

| Constant | Value | Meaning |
|---|---|---|
| `BAND_OUT` / `BAND_IN` | 0.012 / −0.03 | side band outer face (the **only** surface beyond the cells) / inner face (hidden in the parts) |
| band profile | core z −0.20…0.10 · stripe z −0.115…−0.055 (`STRIPE_OUT` 0.018) · plate z 0.10…0.20 · T2+ glow line z 0…0.018 | one merged profile ribbon per outline run (mitred at concave corners) |
| `LIP_W` | 0.11 (0.10–0.12) | trim lip width inward, z `LIP_Z` 0.20…0.235, top edges chamfered 0.006 |
| `BEVEL` | 0.25 × 0.25 | player full-armour convex corner, clipped at runtime (fallback: `armor_bevel_<tier>_<mask>.glb`) |
| `GUARD` | L 0.30 + 0.30, 0.06 thick, z −0.15…0.25 | corner guard on convex corners of functional parts / pirate armour; accent cap = top 0.03 |
| `SEAM` | 0.05 wide, z 0.17…0.206 | one dark seam strip per straight run of inner part seams (T/L junction caps only) |
| `GROOVE` | 0.022 @ 0.16 from the outline | panel groove, hangar / shipyard on High only |

### 3.2 Shaped plates (SL2 E2) – runtime armour plates on the palette atlas

Shaped armour (`wedge`, `chamfer`, `round`, `arc`, `half`, `nose`, `wingL`, `wingR`, `nose2x1`; `src/data/shapes.ts`) has **no GLB**: `src/render/hull/shapePlate.ts` extrudes the shape's **render polygon** (`shapePolygon(shape, 0, 'render')`: 12 chords per quarter circle and per ogive side; the simulation uses 4 / 6) with the deck profile of `parts/common.py`, on the armour template's `AF_Palette` material and attribute layout (+0 draw calls, follows liveries). Built at rot 0 in the part node's frame (x bow, y port, up = three.js +Y) and turned with the node by `rot · 90°` like every part model – except the pad detail (chevrons, seam), which is drawn turned by **−rot · 90° around the pad centroid**, so on the placed plate it **always points to the bow**. Geometry is cached per (shape, style swatches, layout, swatch table); `rot` joins the key only for plates that carry a chevron or a seam (≤ 4 variants per shape and style). **These numbers are the one truth for runtime and Blender** (`shellConstants.ts` "shaped plates"); anything Blender builds for shaped armour (fallback GLBs, icons, mock-ups) follows this table. *In* = inward from the shape outline (mitred at the vertices).

* candidate cells: **inner** full (unshaped) armour cells – all four edge neighbours occupied, each with a fully solid side towards the cell (no edge of the cell on the outline) – minus the cell in front of every muzzle and behind every nozzle;
* a spine is a **straight, one-cell-wide run** of ≥ 3 candidates (`TERRACE_MIN_CELLS`); runs along the bow axis are taken first, then runs across it, each longest first, ties the lowest owner part id;
* a run is taken only if it neither shares nor touches (4-neighbours) a cell of an already chosen spine – spines never merge into a carpet; at most 2 per ship (`TERRACE_MAX_GROUPS`). The spine's geometry belongs to its lowest-id owner part.

## 4. Style guide

**The look:** stylized, colourful, clean sci-fi (No Man's Sky / Astroneer-like) that stays readable from a 55° top-down camera at small size.
* **Hull**: light warm-grey plates (`hull_light`/`hull_white`) over a dark structural core (`hull_dark`), separated by thin dark seams; chunky proportions, chamfered plate corners. Bevels: plates 0.012–0.03, small details 0.004–0.012, stations 0.04–0.07 (always angle-limited, applied before export).
* **Colour roles**: orange = iron tier accent/trim (skirt belt, stripes, chevrons); blue = titanium tier; cyan = engines/thrust/tech glow; pale gold = cruise drive (He3 fuel-cell plasma) and He3 tanks; teal glass = cockpit; violet = gyro; teal-green = reactor; pink = mining laser (+ heavy laser); yellow = fuel; aqua-cyan segments = battery charge; periwinkle blue-violet = tractor beam; warm amber = windows/warning lights/salvage beacon; red/green = port/starboard beacons. Accents are small; the hull stays mostly neutral.
* **Emission**: sparse and purposeful (strengths 1–6 against EMIT_MAX 6). Glows read at game zoom: engine rings, status strips, canopy, crystal ores. Previews use AgX + light bloom; the game uses ACES + bloom.
* **Readability**: every part needs a distinct top-down silhouette/marker (canopy, nozzle, rings, grille, dish…). Check at game zoom (`*-gamescale.png`).
* **Asteroids (final style C)**: deliberate large facets with chamfered edges, per-facet brightness variation + ray-cast AO + resource tint in vertex colour, crevices tinted (never black), 3–4 crystal/ore clusters as the hero feature + small nuggets. Resource colours: iron red-orange prisms, copper gold blocks (+ subtle verdigris stain), ice glowing blue crystals on blue rock, titanium silver blades.
* **Asteroid veins**: recessed chiselled seams with a dark rim and a faceted, slightly glowing ore fill (§2.7.1). Learned in w1–w10: a smooth fill reads as a worm lying on the rock; evenly spaced protruding crystals along the seam read as a caterpillar/zipper (keep them sparse, 0.36–0.62 apart, mostly sunk); strong curvature drifts toward "lightning"; near-parallel veins read as claw marks.
* **Avoid** (the user rejected these): glowing "lightning" cracks along facet edges, wrapped/inlaid bands that read as gift ribbon (a vein must not be a ribbon/band either), flat colour per face with near-black shadow sides, big uniform low-poly blobs, cut-off/awkward hero objects in compositions, nose-on views of reverse thrusters in hero shots.
* **Pirate structures** (`pir_*`): same language as the pirate livery – dark gunmetal, worn plates, rust-red trim, ochre hazard stripes, red/amber glows; scrap-built = mismatched plates with small random tilts, girders, spikes, welded wrecks. Avoid one big clean box (the first launch bay read as a shipping container).
* **Forge-smiths**: see §2.7.5 – keep it clearly separate from both human and pirate styles. Wardens add only the green warden eye (§2.7.11).
* **T3 crystal parts**: violet accents + violet inlay ring + cut-gem corner bars + one hero crystal feature per part (§2.2.2); role colours (teal canopy, pink laser, cyan engine…) never change with the tier.
* **Derelicts**: the human station language faded, dirty, rolled and broken (§2.7.7) – avoid clean beige ("looks like a new station in sepia" was the first pass); damage must read at game zoom: missing arcs, holes, torn wings, drifting pieces.
* **Resource colours (M5a)**: Kr violet crystals, VZ emerald prisms on brown basalt, He3 pale gold glow (comet pockets), Ex magenta (`ex_matter`, icon only until M6a).
* **Stations**: same language at large scale – light decks, dark structure, orange belts, warm window lines, beacons at extremities; a ring or crane gives each a distinct silhouette. **Detail density matches the ship parts** (greeble kit, §2.10) – a large structure must never read as big flat plastic surfaces. Functional surfaces (pads, cradles, build floors, walkways, guide markings) stay clean; detail goes on rims, sides and supporting structure.
* **Planetary bases (M5b)**: the station language on octagonal pads; every module owns ONE bold top-down marker (derrick square, turbine ring, blue wings, radiator X, crate grid, molten crucibles, coil rail, twin-barrel turret, glowing landing ring) – check `m5b-base-top.png` and the orbit shot. Dark pad floors read heavy: keep them `hull_dark`, not `floor_dark`.
* **Drones (M5b)**: colour-coded at game zoom by the top plate – cargo white/orange (big), mining orange top + pink emitter prongs, repair green top + white cross, scout white dart + blue wings.

## 6. Blender 5.2 gotchas

* Render engine enum is `BLENDER_EEVEE` (no `_NEXT`). Dynamic enums can list empty/partial items in background mode (e.g. glTF `export_format`) – just set the value.
* Colour-management *look* names depend on the view transform: under AgX they are `'AgX - Medium High Contrast'` etc. `Standard`, `AgX`, `Raw`, `Filmic`, `Khronos PBR Neutral` exist.
* Compositor: `scene.compositing_node_group = bpy.data.node_groups.new(..., 'CompositorNodeTree')`, add an interface output socket + `NodeGroupOutput`; Glare settings are **inputs** (`glare.inputs['Type'].default_value = 'Bloom'`).
* `Material.use_nodes` is deprecated – new materials already have a node tree.
* `bmesh.ops.create_icosphere(subdivisions=N, radius=…)`: 3 → 320 faces, 4 → 1280, 5 → 5120.
* `matrix_world` is stale after setting `location` until `bpy.context.view_layer.update()`.
* No `Mesh.set_sharp_from_angle`; mark hard edges in bmesh (`edge.smooth = False`) – done in `geo.obj_from_bm`. Bevel `harden_normals` works without auto-smooth.
* `bmesh.ops.bevel(..., clamp_overlap=True)` silently shrinks crack/edge bevels to ~0 on decimated meshes; use `False` with small widths.
* `mathutils.noise` values exceed ±1 – tune thresholds by measuring.
* glTF exporter writes COLOR_0 only with `export_vertex_color='ACTIVE'`; the importer multiplies COLOR_0 into base colour automatically. The "More than one shader node tex image used" warning is harmless.
* Saving a PNG fails if the user has it open in a viewer → `lib/render.render_to` and `write_png` render/save to a temp file and `os.replace` with retries.
* `bpy.context.preferences.filepaths.save_version = 0` avoids `.blend1` backups.
* Text objects: only the built-in font `Bfont Regular` is available headless (don't use system fonts). **Text extrusion is symmetric around the text plane** – give stacked layers (backing plates, swooshes) their own depth bands or they intersect (dark specks).
* Panorama camera: `cam.data.type = 'PANO'`, `cam.data.panorama_type = 'EQUIRECTANGULAR'` (on camera data). Use with an emissive inside-out sphere and Object coordinates for exact equirect textures; render data passes to EXR (`OPEN_EXR`, color depth 32) with view transform `Raw`.
* Orthographic camera with `sensor_fit = 'VERTICAL'`: `ortho_scale` is the vertical extent.
* `Image.save(filepath=…, quality=…)` writes JPEGs after `image.file_format = 'JPEG'`.
* Video: sequencer `scene.sequence_editor_create().strips.new_image(...)` (5.x name `strips`), `render.image_settings.file_format = 'FFMPEG'` (set `media_type = 'VIDEO'` first if present), `ffmpeg.format = 'MPEG4'`, codec `H264`. Works headless.
* Cycles volumes with `film_transparent`: alpha comes only from density – emission alone is invisible in alpha.
* Byte images' `pixels` are the stored (sRGB-encoded, straight-alpha) values – fine for numpy compositing.
* Camera aiming: `(target - loc).to_track_quat('-Z', 'Y')` keeps world-up as image-up.
* GPU: `prefs.compute_device_type = 'OPTIX'; prefs.get_devices(); d.use = d.type == 'OPTIX'; scene.cycles.device = 'GPU'`.
* glTF export writes **every UV map** of a mesh: a second UV layer becomes `TEXCOORD_1` (verified for `Vein_<i>`). On re-import Blender names it `UVMap.001` (the preview renames it to `VeinUV`). `bake_to_atlas` always writes UV layer 0, so create `UVMap` first and keep extra layers at index ≥ 1.
* Boolean modifier `solver = 'EXACT'` carves clean grooves into the decimated, bevelled rocks; carve the rock **before** joining the crystals (the joined mesh has intersecting shells).
* `bpy.ops.object.join` merges UV/colour layers by name; objects without a layer get zeros – set their values afterwards (the vein crystals get their VeinUV that way).
* `BVHTree.FromObject` works in the object's LOCAL space – transform ray origins/directions by `matrix_world.inverted()` once a mesh has a non-identity transform (the giant-core fit first scaled the core to 2 % because of this).
* `bmesh.ops.solidify(bm, geom=faces, thickness=t)` thickens open plates; the returned faces are the new inner side (give them a darker swatch).
* Exporting an **empty** as the root works (`export_glb` selects root + `children_recursive`) – used for `asteroid_giant_*` (root and `Shell` are empties).
* `obj_from_bm` recalculates normals – for deliberately double-sided sheets (accretion disk) build the mesh directly (`anomalies._obj_no_recalc`).
* Per-face colour tints: use the CORNER-domain colour attribute and write all loops of a face (a per-vertex tint smears down the groove walls).
* An `import math` (or any import) placed **inside** a function makes the name local for the whole function → `UnboundLocalError` on earlier uses. Import at module level.
* `asteroids.build()` names its vein children `Vein_0..`; building several veined objects in one scene (Kolos weak points) makes Blender append `.001` – rename the children right after each build.
* Layout JSONs that depend on build results (Kolos veins) must be written **after** the builds (`build_all.LAYOUT_FILES`).
* Planet spheres: `rotation_mode = 'ZYX'` so the spin happens about the planet's own axis **before** the tilt (XYZ spins about world Z after tilting – the bands no longer line up with the ring plane).
* Equirect textures pinch at the poles: anything parked on a planet (bases) must sit near the equator of the texture, or the ground smears into radial streaks (`preview_m5b_base._planet_under` tilts the planet 90°).
* The cloud shell (radius ×1.012) is ABOVE a base on the surface: the game must fade/clear the clouds around a base (the previews drop the cloud shell for base planets).
* Ring/gas giant: the ring glb has its own alpha-blended, double-sided material (`AF_GasGiantRing`) – not the palette atlas; a camera on the side the ring tilts toward sees it wide open and the near arc misses the disc.
* Detail pass: `matrix_world` of freshly built child nodes is stale – `post_dress` calls `view_layer.update()` first (without it children were moved to the origin). `materials.bake_to_atlas` leaves faces that already use AF_Palette alone (so greebles can be joined into finished assets). Joining a mesh without `Col` into one with `Col` gives black – `station_kit._join_kit` adds a white `Col` first.
* Sandbox note: the art agent may not be allowed to delete files – superseded assets go to `art/out/legacy_m5b/` instead.
* The glTF importer DOES apply COLOR_0 (Color Attribute → Mix multiply) – if a weathering pass looks invisible, it is too weak, not missing (check `color_attributes` values).
* Blender 5.2's glTF importer reads the optimized GLBs (`EXT_meshopt_compression`, `KHR_mesh_quantization`, image `uri` relative to the .glb) and WebP images – previews, icons and `.blend` saves work on the shipped files.
* Windows: replacing a file another process holds (dev server, image viewer) fails with EPERM – the optimizer writes to a temp file and retries the rename.
* Bash heredocs containing `'''` break the shell – write patch scripts to a scratch `.py` file. When applying several string replacements in one script, assert each before writing (a partial failure otherwise leaves the file untouched and the next build silently uses old code).
